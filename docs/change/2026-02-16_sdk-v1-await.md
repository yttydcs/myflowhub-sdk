# 2026-02-16 - SDK v1：Awaiter（按 MsgID + SubProto + Action 等待响应）（PR9-SDK-Awaiter）

## 变更背景 / 目标
SDK v0 已统一客户端侧的 Session/Transport，但调用方仍需自行处理“请求-响应等待/超时/取消/重复 req_id”等语义，这会导致：
- Win/CLI/脚本工具重复实现等待逻辑（行为漂移、泄漏风险、维护成本上升）
- 后续协议重构（Server/子协议解耦、assist/up/notify 收敛）时，客户端侧更难保持一致

本次变更目标（SDK v1）：
1) 在 SDK 内新增通用 Awaiter：提供一致的等待语义（timeout/cancel/Close 清理/重复 key 防护）。
2) 匹配规则固定为：`MsgID + SubProto + Action`（更安全，避免误投递）。
3) `SendAndAwait` 当请求 header 的 `MsgID==0` 时，SDK 自动生成非 0 MsgID 并写回 header。
4) 不改 wire、不改 Server/Win，仅在 SDK 内新增能力，为后续 Win 小步迁移做准备。

## 具体变更内容
### 新增（await 包）
- `await/broker.go`
  - `Broker`：进程内等待/投递器（key=`MsgID+SubProto+Action`）
  - 能力：`Register/Deliver/Cancel/Close`；重复 key 返回错误；Close 唤醒并清理全部等待者
  - 性能：维护 `(msg_id,sub_proto)` 二级索引；readLoop 可快速判断是否需要解析 payload.action
- `await/client.go`
  - `Client`：封装 `session.Session` 的 `SendAndAwait`
  - 约束：
    - 仅拦截并投递匹配成功的响应帧（Major=OK/Err + key 命中）
    - 未匹配帧不吞，原样转交给 `onUnmatched`（例如 notify/broadcast/log 等）

## 关键设计决策与权衡
- **匹配粒度选择 `MsgID+SubProto+Action`**：比仅 `MsgID` 更安全，可降低误投递风险（尤其未来多子协议并发时）。
- **仅在存在等待者时解析 payload.action**：通过 `HasMsgSub` 快速路径避免对大量非等待帧做 JSON 解码，减少 CPU/分配。
- **匹配成功帧拦截投递，未匹配帧不吞**：既保证 Awaiter 可用，又不影响 notify/broadcast 等“无等待语义”的帧上报。
- **MsgID 自动生成**：避免调用方忘记设置 MsgID 导致“永远等不到响应”；同时保持 MsgID 非 0 的约束。
